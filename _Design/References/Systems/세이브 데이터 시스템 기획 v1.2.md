# 💡 세이브데이터 시스템 기획서

## 핵심 역할

>
>
>
>
> - 세이브 시스템은 플레이어의 **영구 진행 데이터**를 디스크에 저장하고, 게임 시작 시 이를 복원하는 책임을 가진 시스템이다.
> - 인게임 세션 내 런타임 데이터(적 생존 목록, 현재 웨이브 등, 무기 슬롯 상태)와는 완전히 분리된다. 세이브 시스템이 다루는 것은 세션이 끝난 뒤에도 남아있어야 하는 데이터만이다.
>     - **인게임 무기 슬롯 상태는 저장 대상이 아니다.** 매 게임 시작마다 초기화되며, RDS(런타임 데이터 서브시스템)가 세션 메모리로만 관리한다.
>
> 이하 문서에서 `USaveGameSubsystem`을 **SGS**로 약어 사용.
>
> **핵심 책임**
>
> - 게임 시작 시 디스크에서 세이브 데이터를 로드하고, 런타임 접근이 가능한 형태로 캐싱한다.
> - 다른 시스템의 저장 요청을 수신하여 세이브 슬롯에 반영한다.
> - 인터럽트(강제 종료) 상황에서의 트랜잭션 상태를 저장하여, 재접속 시 일관된 상태를 복원할 수 있도록 보장한다.
> - 저장 데이터를 런타임 데이터시스템에 제공하여 런타임 캐시를 초기화할 수 있도록 한다.
>

---

## 💡 서브시스템 초기화 의존성 순서

SGS는 GameInstance 서브시스템으로 등록되며, 아래 순서로 의존성이 확정된다.

```
1. UGameDataSubsystem       (InitializeDependency)  ← DT 로드 완료 후
2. USaveGameSubsystem       (InitializeDependency)  ← GDS 이후
3. URuntimeDataSubsystem    (InitializeDependency)  ← SGS 로드 완료 후
```

- SGS는 초기화 완료 시 `OnSaveGameLoadedDel`을 Broadcast하여 RDS가 이를 구독하고 런타임 캐시를 초기화하도록 한다.
- SGS는 GDS에 의존하지 않는다. GDS가 먼저 초기화되어야 한다는 순서 보장이 필요한 경우, GameInstance에서 명시적으로 순서를 제어한다.

## 💡 다른 시스템과의 관계

| 연관 시스템 | 관계 방향 | 설명 |
| --- | --- | --- |
| 스테이지 시스템 | 스테이지 → SGS | 스테이지 진입 시(OpenNextStage 직전) 선택 캐릭터 포함 일괄 저장 요청. |
| 레벨업 시스템 | 레벨업 → SGS | 레벨업 UI 진입 중 강제 종료 감지 시 트랜잭션 상태 저장을 요청한다. |
| 무기 시스템 | 무기 → SGS | 강화/진화 트랜잭션 중 강제 종료 감지 시 트랜잭션 상태 저장을 요청한다. |
| 런타임데이터시스템 | SGS → RDS | 게임 시작 시 로드된 세이브 데이터를 OnSaveGameLoadedDel로 전달하여 런타임 캐시를 초기화한다. |
| 설정 시스템 | 설정 변경 → SGS | 설정(볼륨 등) 변경 즉시 저장 요청. |
| GameInstance | GameInstance → SGS | GameInstance 서브시스템으로 등록되어 씬 전환과 무관하게 유지된다. |

>
>
>
>
> - **SGS는 단방향 수신자 원칙을 따른다.**
> - SGS가 다른 시스템에 데이터를 먼저 요청하거나 이벤트를 발생시키는 경우는 초기화 시 런타임 데이터시스템에 데이터를 전달하는 것이 유일한 예외이다.
>

## 💡 저장 데이터 정의

- 세이브 시스템이 관리하는 데이터는 **영구 저장 데이터**, **트랜잭션 상태 데이터**, 두 범주로 구분한다.

### 영구 저장 데이터 (FSaveData)

게임을 종료하고 다시 실행하더라도 유지되어야 하는 플레이어의 누적 진행 데이터이다.

| 데이터 항목 | 타입 | 기본값 | 설명 |
| --- | --- | --- | --- |
| UnlockedCharacterIDs | ARRAY<STRING> | [] | 해금된 캐릭터 ID 목록 |
| LastSelectedCharacterID | FName | NAME_None | 마지막으로 선택된 캐릭터 ID. 스테이지 진입 시 저장. |
| StageRecords | MAP<STRING, FStageRecord> | {} | 스테이지ID → 해당 스테이지의 최고 기록 |
| TotalPlayCount | INT | 0 | 전체 플레이 횟수 누적 |
| TotalClearCount | INT | 0 | 전체 클리어 횟수 누적 |
| TotalGoldEarned | INT | 0 | 전체 누적 획득 골드 (메타 성장 화폐로 사용될 경우를 대비) |
| SettingsData | FRSSettingsData | 기본값 참조 | 게임 설정 데이터. 설정 변경 즉시 저장. |

### FRSSettingsData 구조체 (설정 데이터)

| 필드명 | 타입 | 기본값 | 설명 |
| --- | --- | --- | --- |
| MasterVolume | float | 1.0f | 마스터 볼륨 (0.0 ~ 1.0) |
| BGMVolume | float | 1.0f | BGM 볼륨 |
| SFXVolume | float | 1.0f | SFX 볼륨 |

### FStageRecord 구조체 (스테이지별 최고 기록)

스테이지 기획서에서 위임한 결과 데이터 구조체의 수신 규격이다.

| 필드명 | 타입 | 설명 |
| --- | --- | --- |
| StageID | STRING | 스테이지 고유 ID |
| bIsCleared | BOOL | 클리어 여부 |
| BestSurvivalTime | FLOAT | 최고 생존 시간 (초). 더 높은 값만 갱신한다. |
| BestKillCount | INT | 최고 처치 수. 더 높은 값만 갱신한다. |
| LastKillCountByType | MAP<STRING, INT> | 마지막 플레이의 적 종류별 처치 수 (EnemyID → 수량) |
| LastLootList | ARRAY<STRING> | 마지막 플레이의 획득 전리품 목록 |
| LastTotalExp | INT | 마지막 플레이의 총 획득 경험치 |
| LastTotalGold | INT | 마지막 플레이의 총 획득 골드 |
| PlayCount | INT | 해당 스테이지 플레이 횟수 |

### 트랜잭션 상태 데이터 (FTransactionState)

- 강제 종료 시 진행 중이던 인터럽트 상황을 기록하여, 재접속 시 해당 상황을 복원하기 위한 임시 저장 데이터이다.
- **트랜잭션 상태는 복원 처리가 완료된 즉시 초기화(None)된다.** 재접속 후 처리가 완료되면 해당 필드를 클리어하고 다시 저장하여, 다음 시작 시 중복 복원이 발생하지 않도록 한다.

| 필드명 | 타입 | 설명 |
| --- | --- | --- |
| PendingTransactionType | ENUM | 없음 / 레벨업UI / 무기강화 / 무기진화 중 하나 |
| PendingWeaponCandidateIDs | ARRAY<STRING> | 레벨업 UI 복원용 무기 후보 3종 ID |
| PendingUpgradeWeaponID | STRING | 강화 트랜잭션 복원용 — 강화 완료 대상 무기 ID |
| PendingEvolveResultWeaponID | STRING | 진화 트랜잭션 복원용 — 진화 완료 결과 무기 ID |

## 💡 기능 명세 및 상세 규칙

### 초기화 및 데이터 로드 상세 규칙

>
>
>
>
> - SGS는 **GameInstance 서브시스템**으로 등록된다.
> 게임 실행 시 GameInstance와 함께 초기화되며, 씬 전환과 무관하게 게임 종료 시까지 유지된다.
> - 초기화 시점에 디스크에서 세이브 데이터를 로드한다.(`UGameplayStatics::LoadGameFromSlot`)
> - 세이브 파일이 존재하지 않으면 기본값으로 신규 `FSaveData`를 생성하고, 즉시 저장하여 슬롯을 확보한다.
> - 로드가 완료되면 `OnSaveGameLoadedDel`을 Broadcast하여 RDS가 이를 수신해 런타임 캐시를 초기화하도록 한다.
> - 초기화 완료 여부는 `bIsSaveLoaded` 플래그로 관리한다.
>
> **로드 실패 예외처리:**
>
> - 세이브 파일 없음
>     - 신규 데이터 생성 후 정상 진행
> - 세이브 파일 손상 / 역직렬화 실패
>     - 경고 로그 출력 후 신규데이터로 초기화. 손상된 파일은 백업 경로로 이동 시도
> - 디스크 읽기 권한 없음
>     - 크래시. 플랫폼 경로 및 권한 정보 로그 출력
>

### 저장 트리거 정책

>
>
>
>
> 세이브 데이터는 아래 이벤트에서만 저장된다. 매 프레임·로비 조작 등 빈번한 저장은 금지한다.
>
> | 트리거 | 저장 내용 |
> | --- | --- |
> | 스테이지 진입 시 (OpenNextStage 호출 직전) | LastSelectedCharacterID 포함 FSaveData 일괄 저장 |
> | 설정 변경 즉시 | SettingsData 저장 |
> | 앱 종료 시 (Deinitialize) | FSaveData 전체 저장 |
>
> **NEVER (저장 금지):**
> - 매 프레임
> - 매 로비 조작 (버튼 클릭 등 단순 UI 이벤트)
> - 인게임 무기 슬롯 변경 시 (무기 슬롯은 저장 대상 아님)
>

### 스테이지 결과 저장 상세 규칙

>
>
>
>
> - 스테이지 시스템으로부터 스테이지 결과 정보( `FStageResultData` 구조체)를
> 수신하면 저장 프로세스를 시작한다.
> - 기존 해당 스테이지의 스테이지별 최고 기록(`FStageRecord`)과 수신된 데이터(스테이지 결과 정보)를 비교하여 아래 규칙으로 갱신한다.
>     - 최장 생존시간(`BestSurvivalTime`)은 새 값이 더 크면 갱신한다.
>     - 최대 킬카운트(`BestKillCount`)는 새 값이 더 크면 갱신한다.
>     - 스테이지 클리어 여부(`bIsCleared`)는 한 번 true가 되면 false로 되돌리지 않는다.
>     - 최신 클리어 정보(`LastXxx`) 계열 필드는 항상 최신 플레이 결과로 덮어쓴다.
>     - 플레이 횟수(`PlayCount`)는 항상 1 증가시킨다.
> - 갱신 완료 후 즉시 `SaveGameToSlot`을 호출하여 디스크에 반영한다.
>
> - 예외처리
>
> | 상황 | 처리 |
> | --- | --- |
> | 결과 처리 중 강제 종료 | 집계된 데이터까지 저장.
> 스테이지 기획서와 동일한 원칙으로 미집계 항목은 기본값(0) 처리 |
> | 저장 중 디스크 쓰기 실패 | 경고 로그 출력. 크래시하지 않는다.
> 다음 저장 시도까지 메모리 캐시를 유지한다 |
> | 동일 스테이지가 기록에 없는 경우 | 신규 FStageRecord를 생성하여 Map에 추가한다 |
>

### 트랜잭션 상태 저장 상세 규칙

>
>
>
>
> - 레벨업 시스템 또는 무기 시스템으로부터 트랜잭션 저장 요청을 수신하면, `FTransactionState`의 해당 필드를 채우고 즉시 저장한다.
> - 요청과 함께 전달되는 데이터는 아래와 같이 시스템별로 정해진다.
>
> | 요청 시스템 | 트랜잭션 타입 | 함께 전달되는 데이터 |
> | --- | --- | --- |
> | 레벨업 시스템 | LevelUpUI | 무기 후보 ID 3종 (`PendingWeaponCandidateIDs`) |
> | 무기 시스템 (강화) | WeaponUpgrade | 강화 완료 후 무기 ID (`PendingUpgradeWeaponID`) |
> | 무기 시스템 (진화) | WeaponEvolve | 진화 결과 무기 ID (`PendingEvolveResultWeaponID`) |
>
> **재접속 시 복원 프로세스:**
>
> - 초기화 완료 후 `PendingTransactionType`이 `None`이 아니면 해당 복원 프로세스를 요청 시스템에 알린다.
> - 각 시스템이 복원 처리(UI 재표시, 강화/진화 완료 처리)를 완료하면 SGS에 완료 신호를 보낸다.
> - SGS는 완료 신호 수신 시 `PendingTransactionType`을 `None`으로 초기화하고 다시 저장한다.
>
> **예외처리:**
>
> - 복원 완료 신호 없이 다시 게임이 종료되는 경우
>     - 트랜잭션 상태가 그대로 유지되므로, 다음 재접속에서 동일한 복원 프로세스가 반복된다
> - 트랜잭션 데이터의 무기 ID가 유효하지 않은 경우
>     - 경고 로그 출력 후 해당 트랜잭션 상태를 None으로 초기화. 크래시하지 않는다
>
> ### 저장 방식 및 성능 고려사항
>
> - 세이브 슬롯은 단일 슬롯(`"GameSave"`)을 사용한다. 멀티 슬롯 지원은 미정이며 현재 범위에 포함하지 않는다.
> - 저장은 항상 **동기 방식**으로 실행한다. 세이브 타이밍(스테이지 결과, 트랜잭션 상태)이 모두 게임 시간이 멈춘 상태 또는 종료 시점이므로, 비동기 저장의 이점이 없다.
> - 런타임 중 주기적 자동 저장(Auto-Save)은 구현하지 않는다. 저장은 명시적 이벤트(스테이지 진입, 설정 변경, 앱 종료, 트랜잭션 발생) 시에만 실행된다.
>

## 💡 데이터 스키마

세이브 시스템은 별도의 DataTable을 사용하지 않는다. 모든 데이터는 `USaveGame`을 상속한 `UMySaveGame` 클래스 내 UPROPERTY로 직렬화되어 디스크에 저장된다.

### UVanguardSaveGame 클래스 구성

| UPROPERTY | 타입 | 설명 |
| --- | --- | --- |
| SaveData | FSaveData | 영구 저장 데이터 구조체 |
| TransactionState | FTransactionState | 트랜잭션 임시 상태 구조체 |
| SaveVersion | INT | 세이브 파일 버전 번호. 구조 변경 시 마이그레이션 판단용 |

### SGS 내부 캐시 구조

| 항목 | 설명 |
| --- | --- |
| CachedSaveGame | 마지막으로 로드/저장된 `UVanguardSaveGame` 포인터.
매 조회마다 디스크를 읽지 않기 위해 메모리에 유지한다 |
| bIsSaveLoaded | 초기화(로드) 완료 여부 플래그 |

## 💡 추가 기획 고려 사항

- **캐릭터 해금 조건**
    - `UnlockedCharacterIDs`에 ID를 추가하는 시점과 조건(예: 첫 클리어, 골드 지불 등)이 아직 미정
    - 해금 조건의 트리거 시스템이 명확해지면 SGS에 해금 저장 인터페이스를 추가해야 함
- **SaveVersion 마이그레이션 정책**
