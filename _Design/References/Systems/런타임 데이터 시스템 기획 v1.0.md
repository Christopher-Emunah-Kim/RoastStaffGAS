# 런타임 데이터 시스템 기획서

## 💡 핵심 역할

> 
> 
> 
> 
> - 런타임 데이터 시스템은 **플레이어의 현재 진행 상태를 메모리 위에서 관리하는 중간 계층**이다.
> - GDS가 DataTable에서 읽어온 변하지 않는 정적 데이터를 담당한다면, 
> RDS는 플레이어마다 달라지고 플레이 중에도 계속 변하는 동적 상태를 담당한다.
> - 이하 문서에서 `URuntimeDataSubsystem`을 **RDS**로 약어 사용.
> 
> ### 핵심 책임
> 
> - RDS는 세 가지 범주의 데이터를 관리한다.
>     - **해금 상태 데이터**
>         - SGS로부터 수신한 `UnlockedCharacterIDs`를 런타임 캐시로 보관
>         - 아웃게임 UI(캐릭터 선택 화면, 스테이지 선택 화면)가 해금 여부를 조회할 수 있도록 제공
>     - **선택된 캐릭터 및 세션 초기 상태 데이터**
>         - 플레이어가 캐릭터 선택 화면에서 캐릭터를 선택하면, RDS가 GDS에서 해당 캐릭터의 정적 데이터를 조회하고 비동기 클래스 로드를 수행한 뒤 스폰 준비가 완료된 상태를 유지
>     - **인게임 무기 인스턴스 상태 데이터**
>         - 현재 세션에서 플레이어가 보유한 무기 슬롯의 상태(어느 슬롯에 어떤 무기가 장착되어 있는가, 현재 강화 레벨은 몇인가)를 관리한다.
>         - 무기 시스템이 장착/해제/강화/진화를 처리한 뒤 RDS에 결과를 반영하며, 레벨업 시스템이 무기 후보를 선정할 때 현재 보유 무기 상태를 RDS에서 조회한다.
> 

---

## 💡 다른 시스템과의 관계

- RDS는 SGS와 GDS 양쪽으로부터 데이터를 수신하는 유일한 시스템이다.
- SGS에서는 영구 저장 상태(해금, 기록)를, GDS에서는 정적 스펙(캐릭터 스탯, 무기 정보)을 수신하여 이 둘을 조합한 런타임 표현을 다른 시스템에 제공한다.

| 연관 시스템 | 관계 방향 | 설명 |
| --- | --- | --- |
| SGS | SGS → RDS | 게임 시작 시 SGS가 세이브 데이터를 RDS에 전달하여 런타임 캐시를 초기화한다. |
| GDS | RDS → GDS | 캐릭터 선택 시 GDS에서 정적 데이터(DT_Character)를 조회한다. |
| 무기 시스템 | 무기 ↔ RDS | 무기 장착/해제/강화/진화 완료 시 결과를 RDS에 반영한다. 무기 시스템은 현재 슬롯 상태를 RDS에서 조회한다. |
| 레벨업 시스템 | 레벨업 → RDS | 무기 후보 선정 시 현재 보유 무기 목록을 RDS에서 조회한다. |
| 스테이지 시스템 | 스테이지 → RDS | 세션 종료 시 RDS의 무기 인스턴스 상태를 초기화 요청한다. |
| UI 시스템 | UI → RDS | 아웃게임 UI가 해금된 캐릭터 목록, 스테이지 기록을 RDS에서 조회한다. |

## 💡 관리 데이터 정의

### 1. 해금 상태 캐시

- SGS로부터 전달받은 영구 저장 데이터를 런타임 접근 가능한 형태로 보관한다.
- 이 데이터는 **읽기 전용 캐시**다. RDS는 직접 이 값을 수정하지 않는다. 캐릭터 해금이 새로 발생하면 SGS에 먼저 저장 요청을 보내고, SGS가 저장 완료 후 RDS에 갱신을 통보하는 방식으로 동기화한다.

| 데이터 항목 | 타입 | 설명 |
| --- | --- | --- |
| UnlockedCharacterIDs | ARRAY<STRING> | 해금된 캐릭터 ID 목록. SGS 초기화 완료 시 복사. |
| StageRecordCache | MAP<STRING, FStageRecord> | 스테이지별 최고 기록. SGS 초기화 완료 시 복사. UI 조회용. |

### 2. 선택된 캐릭터 상태 (FSelectedCharacterState)

- 플레이어가 캐릭터 선택 화면에서 선택을 완료한 시점부터 세션 진입까지 유지되는 임시 상태다.

| 필드명 | 타입 | 설명 |
| --- | --- | --- |
| SelectedCharacterID | STRING | 선택된 캐릭터 ID |
| LoadedCharacterClass | STRING | 비동기 로드가 완료된 캐릭터 BP 클래스 경로
스폰 시 사용. |
| bIsCharacterReady | BOOL | 비동기 로드 완료 여부. false인 상태에서는 스폰 불가. |

### 3. 무기 인스턴스 상태 (FWeaponSlotState)

- 현재 세션에서 플레이어가 보유한 무기 슬롯 상태를 관리한다. 슬롯은 0~2번 총 3개다.
- 세션 시작 시 모든 슬롯은 빈 상태로 초기화된다.
- 캐릭터의 `StartingWeaponIDs`에 정의된 시작 무기가 있으면 세션 시작 직후 무기 시스템이 장착 프로세스를 실행하고 RDS에 반영한다.

| 필드명 | 타입 | 설명 |
| --- | --- | --- |
| SlotIndex | INT | 슬롯 번호 (0, 1, 2) |
| WeaponID | STRING | 현재 장착된 무기 ID. 빈 슬롯이면 빈 문자열. |
| CurrentLevel | INT | 현재 무기 강화 레벨 (1~3). 진화 무기는 항상 1. |
| bIsEvolved | BOOL | 진화 무기 여부. 진화 무기는 강화 불가 표시에 사용. |
| SlotType | ENUM | Main / Orbital. 슬롯 타입. DT_Weapon에서 조회하여 캐싱. |

## 💡 기능 명세 및 상세 규칙

### 초기화 상세 규칙

> 
> 
> 
> 
> - RDS는 **GameInstance 서브시스템**으로 등록된다. 
> GDS, SGS와 동일한 생명주기를 가지며 씬 전환과 무관하게 유지된다.
> 
> - 초기화는 두 단계로 나뉜다.
>     - 1단계
>         - SGS 초기화 완료 이후 SGS가 세이브 데이터를 RDS에 전달하면, 
>         RDS가 이를 런타임 캐시(`UnlockedCharacterIDs`, `StageRecordCache`)에 복사
>     - 2단계
>         - 플레이어가 캐릭터를 선택하면, RDS가 GDS에서 해당 캐릭터의 정적 데이터를 조회하고 비동기 클래스 로드를 시작하는 단계
> - 초기화 완료 플래그는 두 단계 각각 독립적으로 관리한다.
> 
> | 플래그 | 설명 |
> | --- | --- |
> | bIsSaveCacheReady | SGS로부터 세이브 데이터 수신 및 캐시 구성 완료 여부 |
> | bIsCharacterReady | 캐릭터 선택 및 비동기 로드 완료 여부 |
> 
> **예외처리:**
> 
> - SGS 초기화 전에 해금 데이터 조회 요청
>     - 요청을 거부하고 경고 로그를 출력한다.
> - 캐릭터 로드가 완료되기 전에 세션 진입 시도
>     - `bIsCharacterReady`가 false인 경우 스폰을 차단하고 로딩 화면을 유지한다.
> - GDS에서 캐릭터 데이터 조회 실패
>     - 크래시. 유효하지 않은 캐릭터 ID로 세션 진입은 허용하지 않는다.
> 

### 캐릭터 선택 처리 상세 규칙

> 
> 
> 
> 
> - 캐릭터 선택 화면에서 플레이어가 캐릭터를 선택하면, 
> RDS는 `SelectedCharacterID`를 갱신하고 GDS에 `DT_Character` 조회를 요청한다.
> - 조회된 `CharacterClass` 경로를 기반으로 `FStreamableManager`를 통해 비동기 BP 클래스 로드를 시작한다.
> - 로드가 완료되면 `LoadedCharacterClass`에 결과를 저장하고 `bIsCharacterReady`를 true로 전환한다.
> - 이후 세션 진입 신호가 오면 저장된 클래스로 캐릭터를 스폰한다.
> 
> **예외처리:**
> 
> - BP 클래스 로드 실패
>     - 크래시. 에셋 경로 오류이므로 게임 진행 불가.
> 

### 무기 슬롯 상태 관리 상세 규칙

> 
> 
> 
> 
> - 무기 시스템이 장착/해제/강화/진화를 처리한 뒤 RDS에 결과 반영을 요청한다.
> - RDS는 요청된 내용을 해당 슬롯의 `FWeaponSlotState`에 반영하는 것만 담당한다.
> - 슬롯 배치 결정, 강화/진화 판단 로직은 무기 시스템의 책임이며 RDS는 관여하지 않는다.
> 
> **슬롯 상태 갱신 요청 규격:**
> 
> | 요청 종류 | 전달 데이터 | 처리 |
> | --- | --- | --- |
> | 장착 | SlotIndex, WeaponID, SlotType | 해당 슬롯의 WeaponID, SlotType 갱신. CurrentLevel = 1, bIsEvolved = false로 초기화. |
> | 해제 | SlotIndex | 해당 슬롯을 빈 상태로 초기화. |
> | 강화 | SlotIndex, 새 WeaponID, 새 CurrentLevel | WeaponID와 CurrentLevel을 갱신. |
> | 진화 | SlotIndex(재료슬롯), 새 WeaponID | 재료 슬롯을 해제하고 새 슬롯에 진화 무기를 장착 상태로 갱신. bIsEvolved = true. |
> | 세션 종료 | 없음 | 모든 슬롯을 빈 상태로 초기화. |
> 
> **예외처리:**
> 
> - 유효하지 않은 SlotIndex(0~2 범위 외)
>     - 경고 로그 출력 후 무시한다. 크래시하지 않는다.
> - 빈 슬롯에 해제 요청
>     - 이미 비어있으므로 무시한다. 경고 로그는 출력하지 않는다.
> - 장착 요청 시 해당 슬롯에 이미 무기가 있는 경우
>     - 무기 시스템이 사전에 해제 후 장착 요청을 보내는 것이 원칙이다. 그럼에도 발생하면 경고 로그를 출력하고 덮어쓴다.
> 

### 해금 상태 조회 상세 규칙

> 
> 
> 
> 
> - UI 시스템과 아웃게임 화면은 RDS에서 해금 상태를 조회한다.
> - 조회 방식은 GDS와 동일하게 복사본 반환 원칙을 따른다.
>     - 조회 요청 시스템이 반환된 배열을 수정하더라도 RDS 내부 캐시에는 영향이 없다.
> 
> - 캐릭터 해금이 새로 발생하는 경우
>     - 해금 조건이 충족되면(해금 조건 트리거는 추후 확정) SGS에 해금 저장을 먼저 요청
>     - SGS가 저장을 완료하면 RDS의 `UnlockedCharacterIDs` 캐시에 해당 ID를 추가
>     - 이 순서를 지켜야 저장 실패 시 런타임 캐시와 디스크 데이터가 불일치하는 상황을 방지할 수 있음.
>

## 💡 데이터 스키마

> 
> 
> 
> 
> - RDS는 별도의 DataTable을 사용하지 않는다. 모든 데이터는 RDS 내부에 메모리 캐시로만 존재하며, 씬 전환 시에도 GameInstance 서브시스템으로서 유지된다.
> 

### RDS 내부 캐시 구조 요약

| 캐시 항목 | 타입 | 설명 |
| --- | --- | --- |
| UnlockedCharacterIDs | ARRAY<STRING> | 해금 캐릭터 ID 목록 |
| StageRecordCache | MAP<STRING, FStageRecord> | 스테이지 최고 기록 캐시 |
| SelectedCharacterState | FSelectedCharacterState | 현재 선택된 캐릭터 상태 |
| WeaponSlots | ARRAY<FWeaponSlotState> | 무기 슬롯 상태 배열 (크기 3 고정) |
| bIsSaveCacheReady | BOOL | 세이브 캐시 초기화 완료 플래그 |

## 💡 아직 고민 중인 사항.

- **해금 조건 트리거**
    - 어떤 시점에 어떤 조건으로 캐릭터 해금이 발생하는지(너무 큰데 규모가)
    - 트리거 확정 후 해당 시스템이 RDS에 해금 요청을 보내는 인터페이스를 추가
- **스테이지 해금 데이터**
    - 현재 SGS의 `FSaveData`에는 스테이지 해금 목록을 추가해두지 않았음(이후 확장)
    - 현재는 `StageRecords`의 존재 여부로 간접 판단은 가능하나
    - 이후 아웃게임 UI에서 "잠금/해금된 스테이지" 표시가 필요하다면 SGS와 RDS 양쪽에 `UnlockedStageIDs` 필드 추가 예정.
